# BYOS repository instructions

- This repository owns reusable BYOS behavior. Consumers must not patch vendored package source or generated bundles; change the kit here, then sync a pinned commit.
- Keep application branding, storage namespaces, session lookup, relay routes, provider selection, and policy gates in consumer bindings. Use existing options, localized strings, headless hooks, and scoped `--byos-*` tokens before adding APIs.
- `@byos/commands` is the shared command palette. It is application UI, not provider behavior, so keep it free of `@byos/core` imports and credentials; applications own their commands, assistant, and icons.
- Reusable provider quick-settings layout, connection-state copy, and picker defaults belong to `@byos/react`; consumers bind provider metadata, settings navigation, and reconnect actions through props.
- Preserve default behavior when extending customization. Validate independent namespaces and custom bindings with synthetic credentials; never include real credentials in commands, output, tests, logs, or commits.
- Browser adapters retain their existing browser-owned credential boundary. The legacy `@byos/codex` adapter still uses verified browser TLS and the bounded ciphertext relay; never add a plaintext fallback to that transport.
- `@byos/server` `createChatGptWebsiteIdentity` is the identity-only website OpenID Connect helper for OpenAI-provisioned commercial partner clients; it remains disabled without the approved client ID and exact callback, and never exposes OAuth tokens. This identity sign-in does not grant ChatGPT plan use. `@byos/chatgpt-local` is the separate official plan-use Sign in with ChatGPT path for a user-owned local runtime. It owns OAuth and calls the public OpenAI Responses API over ordinary verified HTTPS, without the browser TLS relay. Keep its tokens in the OS credential store (macOS Keychain by default), never browser storage, persistent plaintext, command arguments, consumer workspace documents, or hosted application servers. UI bindings receive public connection metadata and model output only. Paid or remotely hosted use requires the applicable OpenAI approval; this local adapter does not grant it.
- Claude token relay boundary: Anthropic's OAuth token endpoint refuses browsers, so `@byos/server` `createClaudeTokenRelay` forwards only the Claude Code client's authorization-code and refresh grants to the fixed `CLAUDE_TOKEN_URL` and returns a filtered response. It never stores or logs a grant or token, accepts no other destination or grant shape, and is the only place a Claude credential crosses a host server (approved 2026-11-01). Inference stays browser to `api.anthropic.com`. Do not widen the allowlist, add logging, or document the paste-code flow as live-verified.
- Grok token boundary: a Grok refresh grant travels only browser to `auth.x.ai` inside browser TLS through the ciphertext `xai-auth` destination, or Node/native directly to `auth.x.ai`; never through a plaintext host relay. The device-code broker is the existing one-time handshake exception. xAI constants and conformance vectors live in `@byos/core` (`xai-oauth.ts`, `conformance/xai-oauth.json`); tests are synthetic, so never claim live xAI success.
- Readable provider tokens, raw provider errors, and TLS keys must never enter diagnostics, persisted checkpoints, analytics, or unrelated backend tools. Browser-adapter provider payloads stay browser-owned. The opt-in local ChatGPT runtime may handle prompts and results needed for the requested inference, but must not log them or expose credentials. Model output is application data, not a safe diagnostic.
- Run `npm ci` and `npm run check` before publishing changes. Root workspace order keeps core before its consumers. Verify both TypeScript-package and static-bundle consumers when sync tooling changes.
- Keep `README.md`, package READMEs, `docs/customization.md`, and `consumers.json` current. Document the concrete capability and limits; do not claim authenticated provider success from synthetic tests.
- Commit scoped changes, push a `codex/` branch (use `codex-` if the remote already has a conflicting `codex` branch), and create a PR. Merge after checks pass. The kit has no production deployment; consumers follow their own release procedures.
